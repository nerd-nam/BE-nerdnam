### 겪은 함정 — 남아 있던 스텁 서버가 만든 벡터가 결과를 바꿨다

처음 돌릴 때는 리포트에 근거가 1개 잡혀서 "검색이 되는 것처럼" 보였습니다. 확인해 보니 그 벡터는 **이전 세션에서 남아 있던
BE 스텁 모드 서버**(8080)가 대기 청크를 재처리하며 넣은 것이었습니다 — `embedding_model = 'stub-embedding:768'`,
즉 실제 AI 서버가 만든 벡터가 아닙니다. 기획서 v1.18 규칙상 저장되면 안 되는 값이라 그 청크 12개를 대기 상태로 되돌렸고
(`embedding_status='PENDING', embedding=NULL, embedding_model=NULL`), 그러고 나서 다시 분석하니 위의 정직한 결과가 나왔습니다.

**연결을 확인하기 전에 어떤 설정의 서버가 떠 있는지 먼저 보세요.** 포트만 보고 재사용하면 이렇게 결과가 오염됩니다.
의심되면 `SELECT embedding_status, embedding_model, count(*) FROM rag.chunk GROUP BY 1,2` 로 확인하면 됩니다.

### 찾은 것 — 계약 기본값 필드에 null 을 보내고 있었다

확인 질문에 "답하기"를 하면 BE 가 사례를 `target_episode` 로 **되돌려 보냅니다**(`mode=episode`).
역할이 비어 있는 사례는 도메인에서 `role = null` 이라, 그대로 보내자 실제 서버가 거절했습니다.

```
422 Unprocessable Entity: {"detail":[{"type":"string_type","loc":["body","target_episode","role"],
                            "msg":"Input should be a valid string","input":null}]}
```

계약의 `role: {type: string, default: ''}` 은 **"없으면 빈 문자열"이지 "null 허용"이 아닙니다.**
BE 스텁은 받아 주기 때문에 실서버에 붙여야 드러났습니다. 같은 모양의 필드를 계약 전체에서 찾아
`infra.ai` 의 record 가 **값을 모를 때 계약 기본값으로 채우도록** 고쳤습니다
(`Episode.role`·목록 4개, `Metric.source`, `RestructureRequest.title`·`skills`·이전·현재 사례,
`MatchRequirement.skills`, `GapRequirement.adjacent`, `GapGuideRequest.tasks`,
`GuideRequest.company`·`position`·`company_intro`·`tasks`, `GuideRequirement.evidence`).
`ApiAiContractTest.보내는_값을_모를_때_계약의_기본값으로_채운다` 가 계약 파일에서 기본값 필드를 읽어
고정하므로, 계약에 기본값 필드가 새로 생겨도 같은 실수가 다시 나지 않습니다.

`scripts/local-smoke.sh --flow` 에도 "확인 질문 답하기" 단계를 넣었습니다. 고치기 전 코드에 대고
돌리면 이 단계가 `ai_error` 로 실패하고, 고친 뒤에는 통과합니다 (둘 다 확인했습니다).

  임베딩해 READY 로 바꿔 놓을 수 있습니다.** 이번에 실제로 겪었습니다 — 포트별로 어떤 설정의 서버가
  떠 있는지 먼저 확인하세요.

## 실행 순서

이미 실행 중인 서버는 먼저 상태·설정을 확인한다. 같은 포트에 두 번째 서버를 띄우지 않는다. 기존 데이터를 지우는 `docker compose down -v`는 사용하지 않는다.

### 1. DB·Redis와 AI 서버

BE 폴더에서 `docker compose up -d postgres redis`. AI 서버는 AI README에 따라 의존성을 설치하고 다음처럼 시작한다. 이미 8000에 서버가 있다면 `/health`의 모드를 확인하고 재사용한다.

```bash
cd /Users/mapi/project/nerdnam/AI-nerdnam
AI_MODE=stub uv run uvicorn app.main:app --host 127.0.0.1 --port 8000
```

첫 연결 점검은 가짜 응답을 주는 FastAPI 서버로 한다. `AI_MODE=real`은 LLM·임베딩 모델 준비와 별도 품질 검증이 필요하다.

### 2. BE → AI 흐름

8099의 기존 BE가 아래 설정으로 실행 중이면 재사용한다. 내부 Java 스텁을 끄는 `nerdnam.ai.stub=false`와 FastAPI의 가짜 응답 모드 `AI_MODE=stub`은 서로 다른 설정이다.

```bash
cd /Users/mapi/project/nerdnam/BE-nerdnam
./gradlew bootRun --args='--server.port=8099 --nerdnam.auth.mode=header --nerdnam.ai.stub=false --nerdnam.ai.base-url=http://localhost:8000'
```

다른 터미널에서:

```bash
cd /Users/mapi/project/nerdnam/BE-nerdnam
bash scripts/local-smoke.sh
bash scripts/local-smoke.sh --flow
```

`--flow`는 로컬 회원 1번에 Redis 기술(이미 있으면 재사용), 이름에 실행 시각이 붙은 테스트 프로젝트·공고를 만들고 아래 흐름을 실행한다. 기존 프로젝트·공고는 수정하지 않는다. 만든 데이터의 id를 출력하고 삭제하지 않는다. 다른 로컬 테스트 회원이면 `MEMBER_ID`를 지정한다.

프로젝트 등록 → 재구성 작업 대기 → 가짜 응답의 확인 질문 빼기 → 사례·프로젝트 확정 → 공고 등록 → 분석 작업 대기 → 리포트 조회 → 지원동기 생성·조회.

`--flow`는 **AI_MODE=stub에서만** 실행한다. 실제 모델의 확인 질문을 자동으로 버리지 않는다. 실패 시 작업 id·오류를 출력하고 멈춘다. 대기 시간 초과는 서버 작업 취소를 뜻하지 않는다. 가짜 임베딩은 저장하지 않으므로 근거가 비고 미충족이 나와도 검색 품질을 평가할 수 없다.

BE의 시작 설정과 FastAPI 접근 로그에서 `/restructure`, `/embed`, `/requirements/extract`, `/match`, `/gap-guide`, `/guide` 호출을 함께 확인한다. API 결과가 완성됐다는 사실만으로 Java 내부 스텁과 실제 HTTP 호출을 구분할 수는 없다.

### 3. FE → BE 화면

```bash
cd /Users/mapi/project/nerdnam/FE-nerdnam
npm ci
API_ORIGIN=http://localhost:8080 npm run dev
```

브라우저에서 `http://localhost:3000`을 연다. FE는 쿠키 세션 인증을 기대하므로 **8080 BE가 `nerdnam.auth.mode=session`으로 실행**돼야 소셜 로그인·동의 흐름을 확인할 수 있다. Google·카카오의 실제 개발용 클라이언트 설정과 콜백 주소도 필요하다. `local` 기본값인 헤더 인증은 FE 로그인 흐름에 바로 쓸 수 없다. 개발용 헤더 인증 BE→AI 테스트와 브라우저 소셜 로그인 테스트를 구분한다.

현재 FE의 API 연결은 로그인·동의·공고 목록 조회/삭제까지다. 기술·경력·프로젝트·검토·라이브러리·공고 입력·리포트·작성 방향 화면은 `features/*/mock.ts`를 참조한다. 해당 화면이 보인다는 이유로 저장·분석까지 실제 연결됐다고 판단하지 않는다.
